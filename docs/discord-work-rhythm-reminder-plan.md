# Discord 업무 리듬 알리미 기획서

## 1. 프로젝트 개요

### 프로젝트명
Discord 업무 리듬 알리미  
(초기명: Discord 쉬는시간 알리미)

### 한 줄 소개
평일 업무 시간에 맞춰 출근, 쉬는시간, 점심, 스크럼, 퇴근 알림을 Discord 채널로 자동 전송하는 서버리스 기반 업무 루틴 자동화 도구. 팀 채널과 개인 채널을 분리해 서로 다른 일정과 문구를 운영한다.

### 개발 배경
인턴 근무 중 장시간 집중하다 보면 쉬는시간을 놓치거나, 점심 종료 및 스크럼 시간을 깜빡하기 쉬웠다. 기존 ChatGPT 알림은 개인 알림에는 적합했지만 팀 Discord 채널에서 함께 확인하기 어렵고, 컴퓨터를 켜두어야 하는 로컬 실행 방식도 장기 운영에 불편했다.

이에 따라 다음 조건을 충족하는 자동화 도구를 기획했다.

- 평일의 정해진 시간에 Discord 메시지 자동 전송
- 컴퓨터가 꺼져 있어도 계속 작동
- Discord 서버 또는 채널을 여러 개 등록 가능
- 알림마다 전송 대상 채널을 지정 가능
- 시간, 요일, 기간, 메시지를 직접 수정 가능
- 특정 알림을 삭제하지 않고 개별 ON/OFF 가능
- 향후 전체 알림을 한 번에 켜고 끌 수 있도록 확장 가능

## 2. 목표

### 핵심 목표
1. 업무 중 휴식 시간을 놓치지 않도록 한다.
2. 출근, 점심, 스크럼, 퇴근 등 하루의 주요 전환 시점을 안내한다.
3. 설정 파일만 수정해 일정과 메시지를 관리할 수 있도록 한다.
4. 팀 알림과 개인 알림을 분리해 서로 영향을 주지 않도록 한다.
5. 로컬 PC에 의존하지 않고 Cloudflare Workers에서 지속 실행한다.

### 비목표
- 복잡한 일정 관리 서비스 제작
- 사용자 계정 및 권한 관리
- 다중 사용자 지원 (계정, 로그인, 사용자별 데이터 분리)
- Notion 공지 내용을 직접 읽어오는 기능
- 휴일 API 연동
- Discord 명령어를 통한 실시간 설정 변경

## 3. 사용자 및 사용 시나리오

### 주요 사용자
- 원격 인턴 및 팀 프로젝트 참여자
- Discord를 업무 채널로 사용하는 소규모 팀
- 정해진 업무 리듬과 반복 알림이 필요한 개인

### 대표 시나리오
1. 오전 9시에 출근 알림과 스크럼·공지 링크를 확인한다.
2. 매시 48분에 쉬는시간 알림을 받아 스트레칭과 수분 섭취를 한다.
3. 오전 11시 48분에 점심시간 알림을 받는다.
4. 오후 12시 50분에 점심 종료 10분 전 안내를 받는다.
5. 스크럼 시간에 Notion 링크를 열어 진행 상황을 정리한다.
6. 오후 6시에 퇴근 알림을 받는다.
7. 주말에는 개인 채널로만 같은 리듬의 알림을 받는다.
8. 팀 활동 기간이 종료되면 팀 알림만 자동 중단되고 개인 알림은 계속된다.

## 4. 기능 명세

### 4.1 예약 알림
각 알림은 자신이 속한 채널(4.7) 안에서 아래 속성을 가진다.

```js
{
  name: "알림 이름",
  time: "09:48",
  message: "Discord로 전송할 메시지",
}
```

`enabled`, `days`, `startDate`, `endDate`는 선택 항목이다. 생략하면 그 알림이 속한 채널의 기본값(4.4)을 따르고, 값을 적으면 그 값이 우선한다 — 단 `enabled`는 채널이 꺼져 있으면 예외이며, 자세한 내용은 4.3을 참고한다. 전송 대상은 별도 필드로 지정하지 않는다 — 알림이 어느 채널 객체 안에 있는지가 곧 전송 대상이다(4.7).

`time` 대신 일정 구간 안에서 반복 전송하려면 `repeat` 필드를 쓴다(4.17).

### 4.2 개별 ON/OFF
각 일정의 `enabled` 값을 수정해 삭제 없이 켜고 끌 수 있다.

```js
enabled: true  // 실행
enabled: false // 중단
```

### 4.3 전체 알림 일괄 ON/OFF
`settings.js`의 최상위 설정으로 모든 알림을 한 번에 제어한다.

```js
export const GLOBAL_SETTINGS = {
  enabled: true,
};
```

Worker는 일정 조회 전에 이 값을 먼저 확인하고, `false`이면 개별 `enabled` 값과 무관하게 전송하지 않는다.

```js
if (!GLOBAL_SETTINGS.enabled) {
  return [];
}
```

최상위 `enabled`는 즉시 중단을 위한 스위치이므로 개별 설정을 덮어쓴다. 반면 채널 기본값(4.4)은 반복 입력을 줄이기 위한 기본값이므로, 요일·기간·시각 등 대부분의 필드는 개별 설정이 채널 기본값을 덮어쓴다. 두 값의 우선순위 방향이 서로 반대인 셈이다.

다만 `enabled` 필드 하나만은 예외다. 채널의 `enabled: false`도 최상위 `enabled`와 같은 방식의 비상정지로 동작해, 그 채널에 속한 모든 항목을 개별 `enabled` 값과 무관하게 제외한다.

```js
function getScheduledItems({settings, schedule}, date) {
  if (!settings.enabled) return [];

  return schedule.filter(
    (entry) =>
      entry.channelEnabled !== false &&   // 채널 자체가 꺼져 있으면 항목의 enabled와 무관하게 제외
      entry.enabled === true &&
      // ...요일·시각·기간 조건
  );
}
```

다른 필드(요일·기간·시각)는 "채널 기본값을 반복 입력하지 않기 위한 편의"이므로 개별 지정이 우선하는 게 자연스럽다. 반면 채널 스위치를 끄는 행위는 "이 채널 전체를 멈추겠다"는 사용자의 명시적 의도이므로, 개별 항목에 남아 있는 `enabled: true` 하나가 그 의도를 무시하고 계속 전송해서는 안 된다. 두 우선순위 규칙이 서로 다른 이유가 여기에 있다.

### 4.4 채널별 기본값
알림은 채널(`team`, `personal` 등) 아래에 소속되며, 채널마다 전송 요일과 운영 기간이 다르다. 이를 알림마다 반복해서 적는 대신 채널 단위 기본값으로 관리한다.

```js
export const GLOBAL_SETTINGS = {
  enabled: true,
  channels: {
    team: {
      enabled: true,
      days: ["Mon", "Tue", "Wed", "Thu", "Fri"],
      startDate: "2026-07-06",
      endDate: "2026-09-09",
    },
    personal: {
      enabled: true,
      days: ["Mon", "Tue", "Wed", "Thu", "Fri", "Sat", "Sun"],
      startDate: "2026-09-06",
      endDate: null,
    },
  },
};
```

채널 기본값은 그 채널의 `items` 배열에 있는 각 알림에 주입된다.

```js
function normalizeSchedule(data) {
  const list = [];
  for (const [name, channel] of Object.entries(data.channels)) {
    const base = {
      enabled: channel.enabled,
      days: channel.days,
      startDate: channel.startDate ?? null,
      endDate: channel.endDate ?? null,
    };
    for (const item of channel.items) {
      list.push({ ...base, ...item, target: name });
    }
  }
  return list;
}
```

개별 알림에 같은 필드가 있으면 그 값이 채널 기본값을 덮어쓴다(단 `enabled`는 채널이 꺼져 있으면 예외 — 4.3). 따라서 대부분의 알림은 이름과 시각, 문구만 적으면 되고, 예외적인 알림만 필요한 필드를 직접 지정한다.

```js
// 채널 기본값을 그대로 사용
{ name: "쉬는시간", time: "09:48", message: BREAK_MSG },

// 이 알림만 비활성화
{ name: "퇴근 알림", time: "18:00", enabled: false, message: "..." },
```

초기에는 모든 알림에 기간을 개별로 적었으나, 기간을 연장할 때마다 전체 알림을 수정해야 해 공통 기본값과 개별 예외를 분리했다. 이후 채널별 저장 구조(KV, 6장)로 옮기면서 이 기본값도 `settings.js`의 상수에서 KV의 `channels.<이름>` 객체로 이동했다.

### 4.5 기간 제한
`startDate`, `endDate`로 특정 기간에만 알림이 동작한다. 값은 채널 기본값에서 관리하며, 알림마다 다르게 지정할 수도 있다.

```js
startDate: "2026-07-06",
endDate: "2026-10-03",
```

`null`을 지정하면 해당 방향의 제한이 없다. 개인 알림은 종료일 없이 무기한 동작하도록 `endDate: null`을 사용한다.

종료일이 지나면 Worker는 계속 실행되지만 메시지는 전송하지 않는다. 이때 오류가 발생하지 않고 조용히 중단되므로, 알림이 오지 않을 때 가장 먼저 확인할 항목이다.

### 4.6 요일 및 시간 설정
요일은 영문 약어 배열로 설정한다.

```js
days: ["Mon", "Tue", "Wed", "Thu", "Fri"],
time: "16:48",
```

시간은 한국 시간 기준 24시간제 `HH:MM` 형식을 사용한다.

### 4.7 채널 구조와 전송 대상
Cloudflare Secret `DISCORD_WEBHOOK_URLS`에 이름과 웹훅 URL을 객체로 등록한다.

```json
{
  "team": "팀 채널 웹훅 URL",
  "personal": "개인 채널 웹훅 URL",
  "test": "테스트 채널 웹훅 URL"
}
```

일정 데이터는 이 이름을 그대로 키로 쓰는 `channels` 객체로 구성된다.

```json
{
  "settings": { "enabled": true },
  "channels": {
    "team": { "enabled": true, "days": ["Mon"], "startDate": null, "endDate": null, "items": [] },
    "personal": { "enabled": true, "days": ["Sun"], "startDate": null, "endDate": null, "items": [] }
  }
}
```

알림이 어느 채널 객체(`channels.team`, `channels.personal` 등) 안에 들어 있는지가 곧 전송 대상이다. 초기 구현에서는 알림마다 `targets: ["team"]`처럼 전송 대상 배열을 따로 적었지만, 실제로는 한 알림이 여러 채널로 동시에 전송되는 경우가 없었고 채널별로 파일도 이미 나눠 관리하고 있었기 때문에 `targets`는 불필요한 중복이었다. 채널 구조(6장)로 옮기면서 제거했다.

KV 데이터가 손상되어 존재하지 않는 채널 이름으로 전송을 시도하면 해당 대상을 건너뛰고 로그에 경고를 남긴다. 오타로 인해 알림이 조용히 누락되는 상황을 방지하기 위한 처리다.

```text
Unknown webhook target: "tema"
```

기존 `DISCORD_WEBHOOK_URLS`의 JSON 배열 형식도 계속 동작하도록 호환 처리를 두었다.

### 4.8 동시간대 다중 알림
같은 시각에 조건을 만족하는 알림이 여러 개 있으면 모두 전송한다. 팀 스크럼과 개인 스크럼처럼 같은 시각에 서로 다른 채널로 다른 문구를 보내는 경우를 지원하기 위한 동작이다.

초기 구현은 일정 조회에 `find`를 사용해 조건에 맞는 첫 항목만 반환했다. 이 경우 요일이 겹치는 순간 나머지 알림이 오류 없이 누락되므로 `filter`로 변경했다.

```js
const items = schedule.filter(/* 조건 */);
for (const item of items) {
  ctx.waitUntil(sendToAll(env, item.message, [item.target]));
}
```

### 4.9 메시지 환경 변수 치환
메시지 안의 `{{변수명}}`은 전송 직전 환경 변수 값으로 치환된다.

```js
message: "🌅️ 좋은 아침입니다!\n오늘 공지 확인 👉️ {{NOTION_URL}}"
```

Notion 링크처럼 저장소에 남기고 싶지 않은 값을 설정 파일에서 분리하기 위한 기능이다. 링크 자체는 Discord 메시지에 정상적으로 표시되며, 저장소에는 자리표시자만 남는다.

미등록 변수는 치환되지 않고 `{{NOTION_URL}}` 형태로 그대로 전송된다. 값이 조용히 비어 전달되는 것보다 누락을 즉시 인지할 수 있어 의도한 동작이다.

### 4.10 테스트 엔드포인트
배포된 Worker 주소 뒤에 `/test`를 붙이면 등록된 모든 웹훅으로 테스트 메시지를 전송한다.

```text
https://<worker-address>.workers.dev/test
```

`/test`는 일정 판별을 거치지 않으므로, 시각·요일·기간 조건을 검증하려면 실제 일정을 임시로 조정해 확인해야 한다.

### 4.11 웹 기반 관리 화면
Worker의 `GET /`는 단일 HTML 관리 화면을 반환한다. 화면 자체는 인증 없이 열리지만, 실제 일정 데이터를 불러오고 저장하려면 관리 토큰을 입력해야 한다(4.12).

화면에서는 채널별 일정 목록을 조회·추가·수정·삭제하고, 채널 ON/OFF·요일·기간을 편집하며, 채널 탭을 길게 눌러 드래그해 표시 순서를 바꿀 수 있다. 순서는 `settings.channelOrder` 배열로 저장되며 알림 발송 로직에는 영향을 주지 않는다. 드래그는 마우스와 터치를 모두 Pointer Events 하나로 처리해 동일하게 동작한다.

변경사항이 있을 때만 저장 바가 나타나며, 저장을 누르면 `PUT /api/schedule`로 전체 데이터를 교체 저장한다. 파일을 직접 열어 수정하지 않아도 되는 것이 목적이므로, 관리 화면과 KV(6장)는 함께 도입했다.

### 4.12 관리 API 인증
`GET /`와 `GET /api/channels`를 제외한 나머지 API(`/api/schedule`, `/admin/init`, `/admin/migrate`, `/test`)는 쿼리 파라미터 `key`가 Cloudflare Secret `ADMIN_TOKEN`과 일치해야 동작한다. 일치하지 않거나 누락되면 `401 { "error": "unauthorized" }`를 반환한다.

비교는 길이를 먼저 확인한 뒤 문자별로 XOR을 누적하는 방식으로 구현해, 타이밍 차이로 토큰 길이나 내용을 추측하기 어렵게 했다.

```js
function timingSafeEqual(a, b) {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) {
    diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  }
  return diff === 0;
}
```

Cron으로 실행되는 `scheduled` 핸들러는 사용자 요청이 아니므로 인증 대상이 아니다.

### 4.13 토큰 인증과 자동 로그인
관리 화면은 최초 접속 시 인증 토큰을 입력받아 브라우저 `localStorage`(`discord-bot-auth-token`)에 저장한다. 이후 방문에는 URL에 `?key=`가 없어도 저장된 토큰으로 자동 로그인되며, 토큰이 만료되었거나(401) 유효하지 않으면 저장값을 지우고 다시 입력 화면으로 돌아간다.

설정 메뉴의 "토큰 재설정"을 누르면 저장된 토큰과 화면 상태를 모두 지우고 즉시 재입력 화면으로 전환된다. 취소 없이 강제로 재인증하도록 만든 이유는, 재설정이 "잘못 입력한 토큰을 고치는" 용도가 아니라 로그아웃에 가까운 동작이기 때문이다.

### 4.14 PWA 지원
관리 화면을 홈 화면에 추가하면 브라우저 주소창 없이 독립된 앱처럼 실행된다. `GET /manifest.json`이 앱 이름("업무 리듬"), 테마색(`#1F7A6D`), 아이콘 목록을 반환하고, `admin-ui.html`의 head에 `apple-mobile-web-app-capable` 등 전체화면 관련 메타 태그를 넣었다. 아이콘은 강조색 배경에 흰 시계 모양이며, 외부 이미지 툴 없이 `scripts/generate-icons.mjs`가 PNG를 직접 인코딩해 생성한다(6장 참고).

일반 아이콘(`purpose: "any"`)과 별개로, Android처럼 OS가 원형·둥근사각형 등 임의 모양으로 잘라내는 maskable 아이콘(`purpose: "maskable"`)도 함께 등록했다. 시계 글자를 캔버스 중앙 80% 안전영역 안에만 그리고 가장자리는 배경색으로 채워, 어떤 마스크 모양을 씌워도 글자가 잘리지 않게 했다. 브라우저 탭 파비콘은 OS가 마스킹을 해 주지 않으므로 별도로 픽셀 자체가 원형인 이미지(원 바깥은 투명)를 만들어 적용했고, 스플래시 화면 배경색(`background_color`)도 아이콘 배경과 같은 강조색으로 맞춰 아이콘이 회색 배경 위에 떠 보이지 않게 했다.

### 4.15 설치 유도 배너
토큰 인증에 성공해 일정 목록을 불러온 시점에, 아래 조건을 모두 만족하면 지연 없이 하단에 설치 유도 배너를 띄운다.

- 이미 홈 화면 앱(standalone)으로 실행 중이 아님
- 배너를 닫은 적이 없거나, 닫은 지 7일이 지남
- 플랫폼상 보여줄 내용이 있음 — iOS는 안내 문구, `beforeinstallprompt`를 받은 브라우저는 설치 버튼

배너를 첫 번째로 닫으면 7일간 다시 뜨지 않고, 두 번째로 닫으면 이후 영구히 자동으로 뜨지 않는다. 반면 실제로 설치를 완료하면(`appinstalled`) 닫음 기록을 남기지 않는다 — 설치는 "다시 보고 싶지 않다"는 의사 표시가 아니기 때문이다. 자동 노출과는 별도로 설정 메뉴에 "홈 화면에 추가" 항목을 상시 배치해, 배너가 영구히 숨겨진 뒤에도 언제든 수동으로 설치를 다시 시도할 수 있게 했다.

### 4.16 채널 탭 드래그 정렬
채널 탭을 길게 눌러 드래그하면 표시 순서를 바꿀 수 있다. 순서는 `settings.channelOrder` 배열에 채널 이름을 나열해 저장하며, 알림 발송 로직(6장)에는 전혀 영향을 주지 않는 화면 전용 값이다. 마우스와 터치를 따로 분기하지 않고 Pointer Events 하나로 처리해, PC와 모바일에서 같은 코드로 동일하게 동작한다.

### 4.17 반복 알림
쉬는시간처럼 정해진 구간 동안 일정 간격으로 반복 전송해야 하는 알림은, 항목을 여러 개 만드는 대신 `time` 대신 `repeat` 하나로 구간 자체를 표현한다.

```js
{
  name: "오전 쉬는시간",
  repeat: { startTime: "09:00", endTime: "11:00", everyMinutes: 60 },
  message: "잠깐 스트레칭하고 물 한 잔 마셔요!",
}
```

`time`과 `repeat`는 상호 배타적이다 — 한 알림은 둘 중 하나만 가지며, 저장 시 둘 다 있으면 오류로 거부한다. 이렇게 나눈 이유는 반복 구간을 시각 여러 개로 미리 펼쳐두면, 시각이나 문구를 바꿀 때마다 펼쳐둔 항목을 전부 찾아 동기화해야 하기 때문이다. 구간 자체를 하나의 값으로 두면 수정·삭제가 그 항목 하나로 끝난다.

전송 여부는 현재 시각이 `startTime`~`endTime` 사이이고, `(현재 시각 - startTime)`이 `everyMinutes`로 나누어떨어질 때 판단한다. **`endTime`은 매칭 범위에 포함**된다 — `09:00`~`11:00`, `everyMinutes: 60`이면 `09:00`, `10:00`, `11:00` 세 번 전송한다. "종료 시각 전까지만"으로 오해하기 쉬운 부분이라 관리 화면에도 같은 안내를 남겨 두었다(4.11).

간격이 구간 길이와 나누어떨어지지 않으면 `endTime`에는 실제로 맞아떨어지지 않는다. 예를 들어 `09:00`~`10:20`에 `everyMinutes: 60`이면 `09:00`, `10:00`까지만 전송되고 `10:20`(마지막 시각)에는 전송되지 않는다 — `(10:20 - 09:00) = 80`분이 60으로 나누어떨어지지 않기 때문이다. 이 경우 구간 안에서 간격 조건을 만족하는 마지막 정시(`10:00`)가 사실상 마지막 전송 시각이 된다. `endTime`을 간격의 배수가 되는 시각으로 맞추면 이런 차이가 없다.

## 6. 시스템 구조

```text
Cloudflare Cron Trigger
        │
        │ 매분 실행
        ▼
Cloudflare Worker (scheduled)
        │
        ├─ KV(SCHEDULE_KV)에서 "schedule" 조회
        │     └─ 없거나 형식이 깨졌으면 src/schedule/ 파일 폴백 사용
        ├─ 전역 설정(settings.enabled) 확인
        ├─ 현재 한국 시간 확인
        ├─ 채널 구조를 평탄화(normalizeSchedule)
        ├─ enabled, 요일, 시각, 기간 확인
        ├─ 조건에 맞는 항목 전부 선택
        └─ 메시지 내 {{변수}} 치환 후 소속 채널로 전송
        ▼
Discord Webhook
        │
        ├─ team
        ├─ personal
        └─ test
```

```text
브라우저 (관리자)
        │
        │ GET /
        ▼
Cloudflare Worker (fetch)
        │
        ├─ GET  /               관리 화면(admin-ui.html) 서빙, 인증 불필요
        ├─ GET  /manifest.json  PWA 매니페스트(이름·테마색·아이콘 목록), 인증 불필요
        ├─ GET  /icon-*.png     아이콘·파비콘 PNG 서빙(icons.js), 인증 불필요
        ├─ GET  /api/channels   DISCORD_WEBHOOK_URLS 키 이름만 반환, 인증 불필요
        ├─ GET  /api/schedule   KV 조회(비어 있으면 파일 폴백), ADMIN_TOKEN 필요
        ├─ PUT  /api/schedule   검증 후 KV 전체 교체 저장, ADMIN_TOKEN 필요
        ├─ POST /admin/init     파일 데이터를 KV에 최초 저장, ADMIN_TOKEN 필요
        ├─ POST /admin/migrate  구 구조 KV를 채널 구조로 변환, ADMIN_TOKEN 필요
        └─ GET  /test           테스트 메시지 전송, ADMIN_TOKEN 필요
        ▼
Cloudflare KV (SCHEDULE_KV)
        ├─ schedule           현재 일정 데이터(채널 구조)
        └─ schedule.backup    /admin/migrate 실행 시 생성되는 이전 구조 백업
```

### 설정 파일 구성

```text
src/
├── index.js         라우팅, 인증, KV 로드/폴백, cron 처리, 전송, manifest.json·아이콘 서빙
├── icons.js          아이콘 PNG를 base64로 담은 번들 (직접 수정 안 함)
├── adminUi.js        admin-ui.html을 감싼 배포용 문자열 번들 (직접 수정 안 함)
├── admin-ui.html     관리 화면 소스 (수정은 항상 이 파일에서)
└── schedule/
    ├── settings.js   전체 ON/OFF, 채널별 기본값(요일·기간)
    ├── team.js       팀 채널 알림 목록(items)
    ├── personal.js   개인 채널 알림 목록(items)
    └── index.js      파일 데이터를 채널 구조로 조립(FILE_SCHEDULE), normalizeSchedule로 평탄화

scripts/
├── build-admin-ui.mjs   admin-ui.html -> adminUi.js 재생성
└── generate-icons.mjs   아이콘 PNG를 직접 인코딩해 src/icons.js 재생성
```

관리 화면 빌드 흐름은 한 방향이다: `admin-ui.html`(원본, 사람이 수정) → `npm run build:admin-ui` → `adminUi.js`(Worker가 `GET /` 응답으로 그대로 서빙). `adminUi.js`는 `admin-ui.html`을 JSON 문자열로 감싼 산출물일 뿐이므로 직접 편집하지 않는다. 아이콘도 같은 구조로, `scripts/generate-icons.mjs`(그림을 그리는 코드) → `npm run build:icons` → `src/icons.js`(base64 산출물, Worker가 `/icon-*.png` 등 경로에서 그대로 서빙) 순으로 재생성한다.

팀 알림과 개인 알림을 파일 단위로 분리한 이유는 두 가지다. 개인 일정을 수정하다 여러 사람이 보는 팀 알림을 실수로 건드리는 상황을 막을 수 있고, 한쪽만 열어 보면 되므로 수정할 항목을 찾기도 빠르다. 팀 활동이 끝나면 해당 파일의 연결만 끊으면 되는 점도 이점이다.

공통 기본값은 두 파일 중 어느 쪽에도 속하지 않으므로 `settings.js`로 분리했다. 한쪽 파일에 두면 다른 파일이 그 파일을 참조해야 해서, 파일을 나눈 이유가 무의미해진다.

`index.js`(schedule 폴더)는 파일들을 조립하는 역할만 한다. KV가 도입된 이후 이 파일들은 최초 배포 시의 폴백 데이터로만 쓰인다 — 실제 운영 중에는 관리 화면이나 `PUT /api/schedule`로 KV 데이터를 직접 수정하며, 파일은 KV 읽기가 비었거나 실패했을 때의 안전장치로 남는다.

### 주요 구성 요소
- **Cloudflare Workers**: 서버리스 실행 환경
- **Cloudflare KV**: 일정 데이터(`schedule`)와 마이그레이션 백업(`schedule.backup`) 저장
- **Cron Trigger**: 매분 Worker 호출
- **JavaScript**: 일정 판별 및 메시지 전송
- **Discord Webhook**: Discord 채널 메시지 전송
- **Cloudflare Secret**: 웹훅 URL, 외부 링크, 관리 토큰 비공개 저장
- **schedule/**: KV가 비었을 때 쓰는 폴백 데이터(시간, 요일, 기간, 메시지)
- **admin-ui.html / adminUi.js**: 브라우저에서 KV 일정을 조회·편집하는 관리 화면
- **icons.js / generate-icons.mjs**: PWA 아이콘(일반·maskable·파비콘) 생성 및 서빙

## 7. 기술 선택 이유

### Cloudflare Workers
- 로컬 PC를 켜둘 필요가 없음
- 무료 범위 내에서 운영 가능
- Cron Trigger 지원
- 배포 및 재배포가 간단함
- 동일 Worker 이름으로 덮어쓰기 배포 가능

### Discord Webhook
- 별도의 Discord Bot 계정이 필요 없음
- 구현과 운영이 단순함
- 지정한 채널로 메시지를 바로 보낼 수 있음
- 이름을 부여해 채널별로 구분 관리 가능

### 설정 파일 분리
실행 로직과 일정을 분리해 시간표 변경 시 핵심 코드를 수정하지 않도록 했다. 이후 운영 대상이 팀과 개인으로 나뉘면서, 설정 자체도 그룹별 파일로 다시 분리했다.

## 8. 배포 및 운영

### 최초 배포

```powershell
npm install
npx wrangler login
npx wrangler kv namespace create SCHEDULE_KV
# 출력된 id를 wrangler.jsonc의 kv_namespaces에 반영
npx wrangler secret put DISCORD_WEBHOOK_URLS
npx wrangler secret put NOTION_URL
npx wrangler secret put ADMIN_TOKEN
npm run deploy
```

배포 직후에는 KV가 비어 있으므로 `src/schedule/` 파일 데이터가 폴백으로 쓰인다. KV에 실제 데이터를 채우려면 한 번 호출한다.

```text
POST https://<worker>.workers.dev/admin/init?key=<ADMIN_TOKEN>
```

이미 KV에 값이 있으면 `409`로 거부해 실수로 덮어쓰지 않는다.

### 설정 변경 후 재배포

```powershell
npm run deploy
```

기존 Worker를 삭제할 필요 없이 같은 주소에 새 코드가 반영된다. 다만 일정 자체는 대부분 재배포 없이 관리 화면(4.11)이나 `PUT /api/schedule`로 KV를 직접 수정해 반영한다.

### 관리 화면 수정 후 재배포

`src/admin-ui.html`을 고친 뒤 번들을 재생성하고 배포한다.

```powershell
npm run build:admin-ui
npm run deploy
```

`adminUi.js`는 `admin-ui.html`을 JSON 문자열로 감싼 결과물이므로 직접 편집하지 않고, 항상 이 스크립트로 재생성한다.

아이콘 디자인(색·모양·크기)을 바꿀 때도 같은 방식으로 재생성한다.

```powershell
npm run build:icons
npm run deploy
```

### 구 구조 KV를 채널 구조로 전환

`targets` 필드를 쓰던 이전 버전에서 이미 `/admin/init`으로 KV를 초기화했다면 한 번 변환한다.

```text
POST https://<worker>.workers.dev/admin/migrate?key=<ADMIN_TOKEN>
```

변환 전 원본은 `schedule.backup` 키에 그대로 보관되며, 이미 채널 구조면 `409`로 거부한다.

### 웹훅 변경

```powershell
npx wrangler secret put DISCORD_WEBHOOK_URLS
```

새 값을 입력하면 기존 Secret이 교체된다. Secret은 재배포 없이 즉시 적용된다.

### 로그 확인

```powershell
npx wrangler tail
```

전송 실패, 알 수 없는 대상 이름, 일정 미매칭, KV 읽기 성공/실패(파일 폴백 여부)를 실시간으로 확인할 수 있다.

## 11. 회고

처음에는 단순히 매시 48분에 쉬는시간을 알려주는 개인 알림으로 시작했다. 하지만 실제 사용 흐름을 점검하면서 점심, 업무 재개, 스크럼, 출근, 퇴근 등 하루의 전환 시점을 함께 관리하는 도구로 확장되었다.

로컬 Python 프로그램은 실행 창을 계속 유지해야 했고 Windows 배치 파일 인코딩 문제도 발생했다. 이를 계기로 실행 환경을 Cloudflare Workers로 전환했고, 컴퓨터 상태와 무관하게 작동하는 구조를 만들었다.

또한 시간과 메시지를 코드에 직접 고정하는 대신 설정 파일로 분리하고, 일정별 ON/OFF와 유효 기간을 추가해 운영 편의성을 높였다.

운영을 이어가면서 설정의 중복도 문제가 되었다. 같은 기간이 모든 알림에 반복되어 연장할 때마다 전체를 수정해야 했고, 이를 공통 기본값과 개별 예외 구조로 정리했다. 저장소 공개를 검토하는 과정에서는 웹훅뿐 아니라 메시지 본문에 포함된 링크도 외부에 노출될 수 있다는 점을 확인하고, 환경 변수 치환 방식으로 분리했다.

운영 대상이 팀 채널 하나에서 개인 채널까지 늘어나면서, 모든 웹훅에 같은 메시지를 보내던 구조로는 주말 개인 알림이 팀 채널까지 도달하는 문제가 생겼다. 웹훅에 이름을 부여하고 알림마다 전송 대상을 지정하는 방식으로 바꾸었다.

이 과정에서 같은 시각에 알림이 하나만 전송되는 제약도 발견했다. 일정 조회에 `find`를 사용해 조건에 맞는 첫 항목만 반환하고 있었고, 요일이 겹치는 순간 나머지 알림이 오류 없이 누락될 수 있는 구조였다. `filter`로 변경해 동시 전송을 지원하도록 했다. 오류를 발생시키지 않고 조용히 실패하는 종류의 문제였기 때문에, 증상이 나타나기 전에 구조를 점검해 발견한 점이 의미 있었다.

설정 파일을 팀과 개인으로 나눌지 판단할 때는, 파일을 적게 유지하는 편이 관리에 유리하다고 보았으나 실제 사용 조건을 따져본 뒤 분리하는 쪽으로 결정했다. 두 알림은 요일도 대상도 목적도 겹치지 않고, 여러 사람이 보는 팀 알림을 개인 설정 수정 중에 잘못 건드릴 위험이 있었기 때문이다. 파일 수보다 실수 가능성을 줄이는 편이 유지보수에 유리하다고 판단했다.

## 설정을 코드 밖으로

설정을 코드 파일에 두는 구조는 오래가지 못했다. 시간 하나를 바꾸려면 파일을 열고, 배포하고,
반영을 기다려야 했다. 외출 중에는 손을 댈 수 없었고, 개인 일정이 그대로 저장소에 커밋되는
문제도 있었다.

일정을 Cloudflare KV로 옮겨 실행 코드와 데이터를 분리했다. 이제 저장소에는 KV를 읽고 쓰는
코드만 남고, 실제 일정은 저장소 바깥에 있다. 앞서 고민하던 "개인 설정 파일을 커밋해야
하는가"라는 문제가 구조 변경으로 함께 해소됐다.

전환 과정에서는 KV가 비어 있거나 읽기에 실패하면 기존 파일을 사용하는 폴백을 먼저 넣었다.
이미 운영 중인 알림이 중간에 끊기면 안 됐기 때문이다. 폴백이 동작하는 것을 확인한 뒤에
초기 데이터를 KV로 옮겼고, 그다음에야 데이터 소스가 실제로 바뀌었는지 로그로 확인했다.

## 중복된 개념을 합치기

채널이 늘어나면서 설정에 `targets`(전송 대상)와 그룹(팀/개인)이 함께 존재하게 됐다.
그런데 실제 운영에서 팀 알림이 개인 채널로 가거나 그 반대인 경우는 한 번도 없었다.
그룹이 이미 채널을 결정하고 있었고, `targets`는 같은 정보를 한 번 더 적는 필드였다.

두 개념을 채널 하나로 합쳤다. 채널이 자신의 기본값과 알림 목록을 함께 갖고, 채널 이름이
곧 전송 대상이 된다. 필드가 하나 줄었을 뿐 아니라 판정 로직도 짧아졌다. 화면에서도
"이 알림을 어디로 보낼지"를 따로 고르지 않고, 채널 탭을 고르면 그 안의 알림은 자동으로
그 채널로 간다.

기능을 추가하다 보면 개념이 늘어나는데, 늘어난 개념 중 일부는 기존 개념과 같은 일을 하고
있다. 그것을 알아채고 합치는 일이 기능을 더하는 것만큼 중요하다는 것을 확인했다.

## 화면을 만들며

관리 화면은 여러 도구를 오가며 만들었다. 처음에는 완성도 있는 결과를 한 번에 얻으려 했지만,
어떤 도구로 만들어도 만족스럽지 않은 시기가 있었다. 시안을 비교하다 보니 어느 것도
완성처럼 보이지 않았다.

돌아보면 문제는 도구나 디자인 감각이 아니라 화면에 올린 정보의 양이었다. 데이터 구조상
필드가 여덟 개이고, 그것을 모두 한 화면에 펼치면 어떤 배치를 써도 복잡해진다.
평소에는 시각·이름·ON/OFF 세 가지만 보이고 나머지는 필요할 때 꺼내도록 바꾸고 나서야
화면이 정리됐다.

또 하나 알게 된 것은, 설정 구조가 확정되기 전에 화면을 만들면 반드시 다시 만들게 된다는
점이다. 채널 구조로 개편하면서 이미 만든 화면을 상당 부분 고쳐야 했다. 데이터 구조를
먼저 확정하고 화면을 만드는 순서가 결과적으로 더 빨랐다.

## 원인을 찾지 못한 채 끝난 문제

운영 중 Cron 실행이 열 시간 가까이 멈춘 일이 있었다. 코드, 설정, 요금제, 트리거 등록
상태를 모두 확인했지만 이상이 없었고, 재배포를 여러 번 해도 살아나지 않다가 어느 순간
저절로 복구됐다. 같은 시기에 분당 두 번 실행되는 현상도 있었는데 역시 시간이 지나
사라졌다.

원인을 밝히지 못한 채 끝났지만, 판단 기준은 하나 남았다. 실행 기록 자체가 없으면
코드가 아니라 실행 환경을 봐야 하고, 실행은 되는데 실패하면 코드를 봐야 한다는 것이다.
처음에는 알림이 오지 않는다는 증상만 보고 설정부터 뒤졌는데, 요청 수가 0이라는 사실을
먼저 확인했다면 훨씬 빨리 범위를 좁힐 수 있었다.

## 편의와 보안 사이

토큰 인증을 처음 붙일 때는 값을 메모리에만 두고 새로고침하면 다시 입력하게 했다.
공용 기기에서 남의 흔적이 남지 않는 안전한 방식이었지만, 실제로 써 보니 휴대폰으로
열 때마다 URL에 토큰을 붙이거나 다시 입력해야 해서 정작 만들려던 편의와 어긋났다.

기기가 개인 휴대폰 하나뿐이라는 실제 사용 조건을 반영해 localStorage에 저장하고
자동으로 로그인되도록 바꿨다. 대신 401을 받으면 저장된 토큰을 즉시 삭제해 만료된
값이 계속 재사용되지 않도록 했고, 설정 화면에 재설정 경로를 남겨 저장된 값을 언제든
지울 수 있게 했다. 보안 원칙을 낮춘 것이 아니라, 원칙을 지키는 방식을 실제 사용
환경에 맞게 바꾼 것에 가까웠다.

## 플랫폼이 정해둔 제약

홈 화면에 앱처럼 설치되게 만드는 과정에서 두 가지를 새로 알게 됐다.

하나는 아이콘 모양이다. 정사각형 이미지를 그대로 등록하면 운영체제가 각지게도,
둥글게도 표시할 수 있는데 어느 쪽으로 나올지는 아이콘 쪽에서 정할 수 없었다.
안전 영역만 채우고 나머지는 배경으로 비워두는 규격(maskable)에 맞춰야 시스템이
일관되게 마스킹해 주었고, 파비콘·홈 화면 아이콘·스플래시 화면이 각각 다른 태그와
설정을 참조한다는 것도 하나씩 확인해야 알 수 있었다.

다른 하나는 갱신 시점이다. 앱 이름, 아이콘, 배경색 같은 설치 정보는 처음 설치할 때
한 번 읽혀 기기에 저장되고, 이후 서버 쪽 설정 파일을 바꿔도 자동으로 반영되지 않았다.
반영하려면 기존 아이콘을 지우고 다시 설치해야 했다. 이런 제약은 코드를 아무리
검토해도 알 수 없고, 실제로 설치해 보고 다시 설치해 보는 과정에서만 드러났다.

디자인을 다듬는 동안은 브라우저로 직접 열어 확인하고, 아이콘과 배경색이 확정된
뒤에만 다시 설치하는 순서로 정리했다. 세부 조정과 설치 확인을 분리한 것만으로
반복되는 재설치 부담이 크게 줄었다.
